# Codex Pro 安装、更新、卸载体验规划

## 1. 目标体验

v0.3.0 的目标不是立刻做 EXE 安装器，而是把现有脚本 + 绿色包体验收口到更像普通 Windows 软件：

- 下载后按 README 执行一次安装。
- 安装后继续像平常一样打开 `Codex`。
- `Codex Pro.cmd` 只是维护 / 救援入口，不是日常主入口。
- 安装、更新、卸载过程尽量不要求用户理解 Node、PowerShell、CDP、bridge、SQLite、rollout 或 provider metadata。
- 出问题时优先告诉用户下一步，而不是展示工程栈细节。
- 所有路径保持本地优先、可回退、可验证。

普通用户应该只记住：

```text
安装一次 → 继续打开 Codex → 历史不完整时点“历史” → 按固定三步恢复
```

固定三步仍然是：

1. 修复历史显示
2. 重建历史索引
3. 打开高级修复

## 2. 当前 v0.2.5 现状

v0.2.5 已经具备首发基础：

- 安装路径是脚本 + 绿色包。
- 已有 `scripts/Install-Codex-Pro.ps1`。
- 已有 `scripts/Uninstall-Codex-Pro.ps1`。
- 已有 `Update Codex Pro.cmd`、`codex-pro update`、`checkForUpdate` 和 `installAvailableUpdate`。
- 已有入口接管与卸载恢复原生入口能力。
- 已有安装 / 卸载 smoke 测试。
- 已有更新失败回滚测试。
- 默认不删除 Codex 历史、历史快照或仓库代码。

当前可发布，但还不像最终普通软件：

- 安装输出已经先显示当前状态、日常入口、下一步、日志位置；v0.3.0 第一轮应继续压低入口状态、开始菜单路径和诊断缓存等维护者信息的噪声。
- 依赖安装阶段仍会出现 `Installing dependencies...`、`Preparing Python launcher...` 等工程提示。
- 更新能力可用，但普通用户对“更新前备份 / 失败回滚 / 更新后重新打开 Codex”的理解还需要更稳定的文案。
- 卸载脚本能恢复入口，但输出仍偏命令行风格。
- 维护入口和日常入口已经分离，但安装后输出需要更明确地避免用户把 `Codex Pro.cmd` 当成日常入口。

## 3. v0.3.0 改进范围

v0.3.0 只做体验收口，不做 EXE 安装器。

优先范围：

- 安装输出四行化。
- 更新提示低噪声。
- 更新前快照 / 备份。
- 更新失败回滚。
- 卸载恢复原生 `Codex` 入口。
- 默认不删 Codex 历史。
- 维护入口清晰命名。
- 错误提示人话化。
- 日志路径只在必要时显示。

建议把安装输出分成两层：

第一层默认只显示：

1. 当前状态
2. 日常入口
3. 下一步
4. 日志位置

第二层只在维护 / verbose 场景显示：

- 桌面 Codex 是否接管
- 开始菜单 Codex 是否接管
- 维护入口完整路径
- 诊断缓存路径
- 各个 `.cmd` 文件路径

## 4. 安装体验设计

### 4.1 安装前确认

v0.3.0 仍然允许脚本安装，但输出要像普通软件：

- 告诉用户将创建维护入口。
- 告诉用户日常仍打开 `Codex`。
- 告诉用户默认不上传历史、不改 provider / API 地址 / 登录方式。
- 告诉用户卸载可恢复原生入口。

不建议默认要求用户理解：

- Node 依赖细节
- Python 依赖细节
- CDP
- bridge
- SQLite
- rollout
- provider identity

### 4.2 环境检查

安装脚本应继续检查：

- Node.js
- npm
- PowerShell 7
- Python launcher
- Codex Desktop 入口或可创建的 Codex 快捷方式

第一层错误文案应写成人话：

```text
还缺一个运行环境。请先安装 Node.js 24+，然后重新运行安装。
```

而不是只展示底层命令失败。

### 4.3 接管入口

安装时继续尽量接管：

- 桌面 `Codex`
- 开始菜单 `Codex`

接管成功后的用户理解应该是：

```text
以后继续打开 Codex。
```

接管失败时不应写成“安装失败”，而应写：

```text
当前暂未接管原生 Codex 入口。维护入口仍可用；确认已安装 Codex 后，可以重新运行安装脚本。
```

### 4.4 创建维护入口

维护入口继续放在：

```text
开始菜单 -> Codex Pro
```

维护入口建议保持：

- `Repair History`
- `Protection Status`
- `Update Codex Pro`
- `Injection Check`
- `History Check`
- `Quick Start`
- `Uninstall`

桌面 `Codex Pro.cmd` 继续保留为维护 / 救援入口，但文案必须强调：

```text
平时不用打开 Codex Pro.cmd，继续打开 Codex。
```

### 4.5 首次快照

安装时继续创建首次历史快照。

用户文案：

```text
已创建首次历史快照，后续修复或删除前也会优先保留可恢复路径。
```

不建议第一层展示快照文件路径。

### 4.6 安装输出四行

v0.3.0 默认安装完成输出建议固定为：

```text
安装完成
当前状态：原生入口已接管 / 兼容模式继续可用 / 等待本机确认
日常入口：继续打开 Codex
下一步：历史不完整时，在 Codex 里打开“历史”，先点“修复历史显示”
日志位置：%USERPROFILE%\.codex-pro\launcher.log
```

如果当前历史有风险，下一步改为：

```text
下一步：继续打开 Codex；如果历史不完整，先点“修复历史显示”，再点“重建历史索引”
```

如果没有接管原生入口，下一步改为：

```text
下一步：先用维护入口临时启动；确认已安装 Codex 后重新运行安装脚本
```

## 5. 更新体验设计

### 5.1 检查更新

更新可以自动检查，但不能静默安装。

第一层文案：

```text
发现新版本。可以现在更新；更新后重新打开 Codex。
```

如果检查失败：

```text
这次没有检查到更新信息。Codex Pro 不会阻塞启动，可以稍后再试。
```

### 5.2 用户确认后更新

更新必须由用户确认触发：

- Codex 内高级区点击更新
- 开始菜单 `Update Codex Pro`
- CLI `codex-pro update`

不做：

- 静默强制更新
- 开机自动更新
- 后台偷偷替换

### 5.3 更新前备份

更新前必须备份当前版本的可替换文件。

用户文案：

```text
更新前会先备份当前版本；如果更新失败，会恢复到更新前状态。
```

不建议第一层展示临时备份目录。

### 5.4 更新失败回滚

如果依赖刷新、包解压或文件替换失败，应回滚。

第一层文案：

```text
更新没有完成，已恢复到更新前状态。你可以继续正常打开 Codex。
```

高级日志再保留：

- npm 错误
- tar 错误
- Python 依赖错误
- 文件复制错误

### 5.5 更新后仍继续打开 Codex

更新成功后只告诉用户：

```text
已更新。请关闭并重新打开 Codex，切到新版本。
```

不要要求用户改日常入口。

### 5.6 不注册开机自启

v0.3.0 仍然不注册开机自启。

轻量守护只服务历史保护，不扩成长期后台更新器。

## 6. 卸载体验设计

卸载目标：

- 停止轻量守护。
- 恢复原生 `Codex` 入口。
- 移除 Codex Pro 创建的维护入口。
- 默认不删除 Codex 历史。
- 默认不删除历史快照。
- 默认不删除仓库代码。
- 只有显式 `-RemoveData` 才清理工具私有数据。

建议卸载完成输出：

```text
卸载完成
原生入口：已恢复 Codex
保留数据：Codex 历史、历史快照和仓库代码未删除
如需清理工具私有数据，请重新运行卸载并显式使用 -RemoveData
```

如果入口恢复失败，第一层文案：

```text
卸载已完成，但原生 Codex 入口需要手动确认。你的 Codex 历史没有被删除。
```

## 7. 错误文案原则

普通用户第一层文案不要出现：

- CDP
- bridge
- SQLite
- rollout
- provider identity
- stack trace
- token
- port

第一层错误文案应该回答：

1. 现在还能不能继续打开 Codex？
2. 历史有没有被删除？
3. 下一步点什么？
4. 日志在哪里？

示例：

```text
当前先按兼容方式继续使用。Codex 仍可正常打开，历史保护仍可用。
下一步：打开“历史”，先点“修复历史显示”。
日志位置：%USERPROFILE%\.codex-pro\launcher.log
```

高级区 / 日志中才保留工程细节。

## 8. v0.3.0 不做清单

v0.3.0 不做：

- EXE 安装器。
- 静默自动更新。
- 开机自启。
- 自动修改 `model_provider`。
- 自动修改 `base_url`。
- 自动切换登录方式。
- 重写 `encrypted_content`。
- 删除 Codex 历史。
- 删除历史快照。
- 引入云服务。
- 引入新的长期后台服务。
- 扩成插件市场或 provider 管理器。

这些边界必须继续写进 README、release notes 和安装 / 更新 / 卸载输出。

## 9. 验收标准

v0.3.0 的体验验收标准：

- 小白能按 README 完成安装。
- 安装完成默认只需看四行。
- 用户知道以后继续打开 `Codex`。
- 用户知道 `Codex Pro.cmd` 只是维护 / 救援入口。
- 用户知道历史异常时优先打开 `历史`。
- 更新必须有用户确认。
- 更新前有备份。
- 更新失败能回滚。
- 更新后提示重新打开 Codex。
- 卸载会恢复原生入口。
- 卸载默认不删除 Codex 历史、历史快照或仓库代码。
- install smoke 通过。
- update install rollback 测试通过。
- pack 清单干净。
- 不打开真实 Codex 也能做脚本级 smoke。
- 不出现静默更新、开机自启、云同步或 provider 自动切换承诺。

## 10. 下一轮实现优先级

如果进入 v0.3.0 实现，建议按下面顺序：

1. 收敛 `scripts/Install-Codex-Pro.ps1` 默认输出，只保留四行结果；把详细路径和端口移到维护 / verbose 输出。
2. 收敛 `scripts/Uninstall-Codex-Pro.ps1` 输出，明确原生入口恢复和默认保留数据。
3. 收敛 `src/update-install.js` 的成功 / 失败文案，确保第一层只说“已更新 / 已回滚 / 重新打开 Codex”。
4. 增强 `test/install-flow.test.js` 对四行输出的断言。
5. 增强 `test/update-install.test.js` 对“失败后已恢复、继续打开 Codex”的断言。
6. 更新 `docs/quick-start-zh.txt`，让安装、更新、卸载入口更像普通软件说明。
