# Codex Pro 原生 UI 指南

> 这份文档用于约束 `Codex Pro` 在 Codex Desktop 内的注入 UI：它应该像 Codex 自己补上的历史恢复能力，而不是一个外挂面板、开发者工具箱或 Codex++ 式功能菜单。本文件是 UI 原生感、低工具感和 Codex++ parity 能力进入 UI 的审计依据。

## 1. 目标

`Codex Pro` 的 UI 目标不是“展示所有能力”，而是让普通用户在 Codex 里自然完成一件事：

```text
历史没显示完整时，点「历史」，按一个主路径恢复。
```

UI 必须做到：

- 第一眼像 Codex 原生功能。
- 第一层只解决历史恢复主问题。
- 高级能力默认折叠。
- 删除、导出、Timeline、插件修复不打扰普通用户。
- 工程诊断词只进入高级区、日志或维护者文档。
- compatibility mode 表达为安全回退，不表达为失败。
- Codex++ parity 能力必须通过 UI 层级准入，不允许直接堆进主路径。

## 2. Codex Pro UI 的一号原则

> 普通用户只应该看到当前状态、一个人话解释、一个主按钮和明确的安全边界。

如果一个 UI 元素不能回答下面任一问题，它默认不应该进入第一层：

1. 历史是不是没显示完整？
2. 我下一步该点什么？
3. 这一步会不会乱改账号、模型或 API 地址？

第一层不是功能总览，不是诊断面板，不是开发者控制台，也不是 Codex++ parity 展示区。

## 3. 第一层 UI 允许出现什么

第一层允许出现：

- 入口名：`历史`
- 一句状态：
  - `历史可能没显示完整`
  - `正在检查历史`
  - `历史显示正常`
- 一句解释：
  - `本地记录还在。点一下，让它重新显示。`
  - `继续像平常一样打开 Codex。`
- 一句安全说明：
  - `不会改账号、模型或 API 地址。`
- 一个主按钮：
  - `修复历史显示`
  - `重建历史索引`
  - `打开高级修复`
  - `检查一次`
- 一个默认折叠的 `高级`
- 低噪声 footer：
  - `保护会在需要时检查，平时尽量不打扰。`

第一层推荐结构：

```text
历史

历史可能没显示完整
本地记录还在。点一下，让它重新显示。
不会改账号、模型或 API 地址。

[修复历史显示]

高级
```

## 4. 第一层 UI 禁止出现什么

第一层禁止出现：

- `CDP`
- `bridge`
- `SQLite`
- `rollout`
- `provider identity`
- `session_index.jsonl`
- `workspace roots`
- `token`
- `localhost`
- `端口`
- `selector`
- `注入失败`
- `诊断失败`
- `debug`
- `Doctor`
- `Guard Status`
- `Diagnose Injection`
- `破解`
- `绕过`
- `强制`
- provider / API / 登录方式的操作建议
- 多个同级主按钮
- 长列表
- 功能矩阵
- 开发者命令

这些词可以进入高级诊断、日志、README 维护者区或 release evidence，但不能进入普通用户第一层路径。

## 5. 历史入口规则

历史入口应该：

- 优先命名为 `历史`。
- 尽量挂在 Codex 原生导航或侧栏语境里。
- 视觉上跟随 Codex 原生字体、间距、颜色和 hover 状态。
- 不使用强品牌露出，不写 `Codex Pro 控制台`。
- 不在 sidebar / header 同时制造多个醒目入口。
- floating fallback 只作为找不到原生挂载点时的兼容入口，不作为首选体验。

历史入口不应该：

- 命名为 `历史与修复`。
- 命名为 `Guard Status`、`Doctor` 或 `Diagnose Injection`。
- 使用强烈发光点、玻璃球、彩色徽章或营销式图标。
- 让用户误以为必须打开一个新工具才能使用 Codex。

## 6. 右侧救援卡规则

右侧面板应该像“救援卡”，而不是“工具面板”：

- 贴近 Codex 侧边栏 / 右侧 sheet 语义。
- 白色或接近原生 Codex 的安静背景。
- 低阴影、低边框、低动画。
- 只有一个主卡片。
- 只有一个主按钮。
- 高级区默认折叠。
- 主卡文案必须短、人话、非工程化。

右侧面板不应该：

- 做成全屏仪表盘。
- 使用大面积液态玻璃、强毛玻璃、强渐变、强光斑。
- 同时展示多张同级状态卡。
- 在第一层展示 provider、SQLite、rollout、index、roots 等工程状态。
- 把安装、更新、导出、插件修复、Timeline 都放成第一层按钮。

当前源码审计结论：

- 最终覆盖层已经把早期玻璃感 CSS 收敛成右侧原生 sheet，方向正确。
- 早期 CSS 中仍保留较多 `Liquid glass` / glass polish 覆盖段，最终视觉被后续 minimal layer 覆盖，不构成首发 UI blocker，但会增加后续维护阅读成本。
- v0.3 / v0.4 不建议继续叠 CSS 覆盖层；如果要继续优化，应先整理分区，再小步删除或合并死样式。

## 7. 会话行 action 规则

会话行 action 必须是二级动作：

- 只在 hover / focus 时出现。
- 不抢原生会话标题和时间位置。
- 不遮挡原生状态。
- 当前会话不显示删除。
- 有原生右侧状态的行不注入删除按钮。
- 删除、导出、移动都不能默认常驻显示。

会话行 action 不应该：

- 在所有行常亮。
- 用红色危险图标吓用户。
- 在当前会话上提供删除。
- 把多个按钮挤到侧栏第一层。

当前源码审计结论：

- 删除按钮当前符合 hover / focus 二级 action 规则。
- 代码中有 `isCurrentSessionRow(row, threadId)` 和 `hasNativeRightStatus(row)` 防误挂逻辑，方向正确。
- 删除按钮视觉最终层为透明背景、弱灰图标，低工具感。

## 8. 删除按钮规则

删除按钮必须：

- 使用 `移除会话` 这类低冲击文案，避免一上来写“永久删除”。
- 删除前二次确认。
- 明确删除前会创建快照。
- 明确可撤销。
- 当前会话不显示删除按钮。
- 删除失败时说明本地历史没有被改动。

删除按钮禁止：

- 批量删除。
- 当前会话删除。
- 无确认删除。
- 无撤销删除。
- 红色高危常驻按钮。

当前源码审计结论：

- 侧栏删除确认文案克制：`移除这条会话？`
- 删除前说明自动创建快照、可撤销。
- 删除失败文案强调本地历史没有被改动。
- 高级搜索结果里的删除仍使用 `window.confirm`，可接受但略偏系统工具感；后续如优化，应复用同一套轻量 confirm card，不改变删除逻辑。

## 9. 导出按钮规则

导出按钮必须：

- 位于高级区或会话行二级 action。
- 默认只做单会话导出。
- 不上传。
- 不调用外部模型。
- 不包含密钥、token、`auth.json` 或旧加密内容原文。
- 输出失败时说明本地历史没有被改动。

导出按钮不应该：

- 进入第一层主路径。
- 暗示会云同步。
- 暗示会自动总结或上传给 AI。
- 和删除按钮并列成普通用户主操作。

当前源码审计结论：

- 导出 Markdown 和生成交接包都在高级搜索结果中出现，层级可接受。
- 文案 `导出 Markdown`、`生成交接包` 清晰。
- 后续应继续按 `docs/redaction-and-privacy.md` 接入 redaction fixture。

## 10. Timeline 规则

Timeline 必须：

- 只作为长对话辅助能力。
- 默认不抢主路径。
- 只扫描当前页面已经显示的内容。
- 可手动生成。
- 可隐藏。
- 不接管滚动主体。
- 不承诺完整全局导航。

Timeline 不应该：

- 默认常驻右侧。
- 在普通历史恢复主路径中自动展开。
- 输出过多摘要导致隐私风险。
- 把当前页面 mock 当真实 Codex 体验。

当前源码审计结论：

- Timeline 当前放在高级区。
- 有 `生成跳转点` 和 `隐藏跳转点`。
- 文案明确只看当前页面已经显示的提问。
- 空状态里有“当前 Codex 版本暂时没有暴露可识别的用户消息结构”，略偏工程化；由于它在高级区，暂不构成首发 blocker。后续可改为更人话的“当前页面还没有可识别的提问”。

## 11. 插件修复规则

插件修复必须：

- 放在高级区。
- 使用 `显示插件入口`、`恢复安装按钮`。
- 说明不会改账号、模型或 API 地址。
- 失败时给人话原因。
- 不保证所有插件都能安装。

插件修复禁止：

- 使用“破解”。
- 使用“绕过”。
- 使用“强制”。
- 暗示切换登录方式。
- 暗示伪造账号。
- 暗示修改 Codex 安装包。

当前源码审计结论：

- 当前按钮文案为 `显示插件入口`、`恢复安装按钮`，符合要求。
- 未发现用户可见的“破解 / 绕过 / 强制”文案。
- 插件修复在高级区，层级正确。

## 12. 兼容模式文案规则

compatibility mode 必须表达为安全回退：

- `当前先按兼容方式继续使用，历史保护仍生效。`
- `这次页面增强没有挂到当前窗口，但不会影响历史保护、快照、修复历史、重建索引和删除撤销。`
- `继续像平常一样打开 Codex 即可。`

禁止表达为：

- `注入失败`
- `启动失败`
- `功能不可用`
- `请改用另一个入口`
- `当前安装失败`

兼容模式必须让用户知道：

- Codex 仍可用。
- 历史保护仍可用。
- 固定三步仍可用。
- 页面增强是否成功不等于历史恢复是否可用。

当前源码 / 文档审计结论：

- launcher 和 README 已将兼容模式表达为安全回退，不是失败页。
- 注入诊断细节主要在高级 / 维护入口，不进入第一层 UI。
- 本轮未运行 `validate-real-codex-ui.py`，因此真实 UI 模式仍以已有 `artifacts/real-codex/validation-summary.json` 为准。

## 13. 高级区规则

高级区可以包含：

- 当前历史 / 本地记录 / 当前项目 / 当前显示摘要。
- 插件入口显示。
- 恢复安装按钮。
- 长对话跳转。
- 找回旧会话。
- 导出 Markdown。
- 生成交接包。
- 当前保护。
- 最近一次检查。
- 快照 / 恢复快照。
- 暂停 / 恢复守护。
- 打开日志目录。
- 检查更新。
- 更多修复入口。
- 卸载说明。

高级区必须：

- 默认折叠。
- 有简短说明。
- 不替代第一层主路径。
- 工程词尽量隐藏在结果、日志或维护文档里。

高级区不应该：

- 默认展开。
- 变成一个全部能力平铺的菜单。
- 使用多个同级危险按钮。
- 让普通用户以为必须理解所有卡片才能恢复历史。

当前源码审计结论：

- 当前使用 `<details class="chg-advanced">`，没有 `open` 属性，默认折叠。
- 高级区文案说明“需要找回旧会话、恢复快照、撤销删除或看兼容说明时，再打开这里”，方向正确。
- 高级区内容已经较多，是 v0.4 parity 阶段的主要拥挤风险；新增能力前必须先归类和收纳。

## 14. 错误文案规则

错误文案应该：

- 短。
- 人话。
- 告诉用户下一步。
- 告诉用户有没有改动本地历史。
- 不暴露 token、路径、`auth.json`、旧加密内容原文。

推荐文案：

- `本地状态暂时没有连上。稍后再试一次。`
- `这次没有移除成功。本地历史没有被改动，可以稍后再试。`
- `这次没有导出成功。本地历史没有被改动，可以稍后再试。`
- `这次没有完成更新。当前版本仍可继续使用，可以稍后再试。`
- `当前先按兼容方式继续使用，历史保护仍生效。`

错误文案不应该：

- 直接显示 stack trace。
- 直接显示本地绝对路径。
- 显示 token、key、cookie。
- 写成 `bridge failed`、`CDP failed`、`SQLite error` 这类第一层工程错误。

当前源码审计结论：

- `friendlyError()` 默认返回人话 fallback，并把细节留在 debug，方向正确。
- 多数 action 的失败文案都强调“本地历史没有被改动”或“当前版本仍可继续使用”。
- 后续 bridge errors 应继续接入统一 redaction。

## 15. Codex++ parity 功能进入 UI 的准入规则

任何 Codex++ parity 能力进入 UI 前，必须先回答：

1. 它属于第一层、第二层、高级区、维护入口，还是不进入 UI？
2. 它是否会改变本地历史、索引、SQLite、workspace roots 或 provider metadata？
3. 它是否需要快照？
4. 它是否需要二次确认？
5. 它是否需要 redaction？
6. 它是否可能让用户误以为会改 provider、`base_url`、登录方式或 `encrypted_content`？
7. 它是否会增加第一层按钮数量？
8. 它是否会让 Codex Pro 看起来像外挂工具合集？

准入判断：

- **插件入口显示**：高级区；不改账号 / 登录；不写破解。
- **插件安装按钮恢复**：高级区；不承诺所有插件可装。
- **单会话删除**：二级 action；快照；确认；撤销。
- **Markdown 导出**：高级区 / 二级 action；redaction。
- **会话项目移动**：高级区；快照；二次确认；一致性验证；v0.4 之前不进主路径。
- **Timeline**：第二层 / 高级区；默认不常驻；可隐藏。
- **Provider 可见性修复**：历史恢复中心内部能力；不做 provider 管理器。
- **Recovery Evidence**：高级区 / issue flow；必须 redaction。
- **Context Risk**：第二层低噪声提醒；不承诺突破上下文限制。
- **批量删除**：不进入 UI。
- **插件市场**：不进入 UI。
- **静默自动更新**：不进入 UI，不做。

## 16. 验收 checklist

每次 UI 改动后至少检查：

- [ ] 第一层入口是否仍叫 `历史`。
- [ ] 第一层是否仍只有一张救援卡和一个主按钮。
- [ ] 第一层是否没有 CDP、bridge、SQLite、rollout、provider identity 等工程词。
- [ ] 固定三步是否仍清楚：修复历史显示、重建历史索引、打开高级修复。
- [ ] 高级区是否默认折叠。
- [ ] 删除按钮是否只在 hover / focus 时出现。
- [ ] 当前会话是否不显示删除。
- [ ] 删除前是否确认。
- [ ] 删除前是否快照，删除后是否可撤销。
- [ ] 删除 / 导出 / Handoff 失败时是否说明本地历史没有被改动。
- [ ] Timeline 是否可隐藏。
- [ ] 插件修复是否没有“破解 / 绕过 / 强制”文案。
- [ ] compatibility mode 是否表达为安全回退。
- [ ] 更新是否需要用户确认，不是静默安装。
- [ ] UI contract 测试是否覆盖关键入口和文案。
- [ ] 如果改了 `inject-ui/history-guard-ui.js`，是否运行 `node --check inject-ui\history-guard-ui.js`。
- [ ] 如果影响真实页面融合，是否在不打断当前环境的前提下安排真实 Codex UI 验收。

## 17. 本轮专项审计结论

基于源码、测试、产品文档和现有验证资产的只读审计，本轮判断：

- 第一层 UI 基本符合“原生历史救援卡”方向。
- 主入口叫 `历史`，文案人话。
- 主卡存在明确安全说明：不会改账号、模型或 API 地址。
- 高级区默认折叠。
- 删除按钮仍是 hover / focus 二级 action，当前会话有防误挂逻辑。
- Timeline、插件修复、导出、Handoff 均未进入第一层。
- compatibility mode 文档和 launcher 口径是安全回退，不是失败页。
- 真实 Codex UI 本轮未重新运行；如要发布前最终确认，仍应跑 takeover-first 的真实 UI 验证。

非阻塞风险：

- `inject-ui/history-guard-ui.js` 内部 CSS 历史覆盖层较多，虽然最终视觉已收敛，但维护成本偏高。
- 高级区能力已经较多，v0.4 做 Codex++ parity 时有膨胀风险。
- Timeline 空状态有一句偏工程化文案，但位于高级区，暂不阻塞。
- 本地 `inject-ui/preview.html` 已不存在；不能再把本地网页 mock 当真实体验依据。
